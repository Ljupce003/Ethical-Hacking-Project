## 3. JWT: формат, граници на доверба и типични грешки

### 3.1. Што е JWT и како се поврзува со OAuth?

JSON Web Token (JWT) е формат за пренос на тврдења (*claims*). Најчестата форма е потпишан токен составен од три Base64URL-енкодирани дела:

```text
header.payload.signature
```

Во `header` се наведува, меѓу другото, алгоритмот `alg`. Во `payload` може да стојат кориснички идентификатор, улога, издавач (`iss`), примач (`aud`) и време на истекување (`exp`). Третиот дел е потпис. Првите два дела **не се шифрирани**: секој што го поседува токенот може да ги прочита. Потписот служи за проверка дека содржината не е изменета и дека е потпишана со очекуваниот клуч; тој не ја крие содржината [6].

OAuth 2.0 и JWT не се заменливи поими. OAuth го уредува добивањето делегиран пристап, додека JWT е можен формат на токен. OAuth access token може да биде и непроѕирна случајна низа. Кај OpenID Connect, ID token е JWT што клиентот го проверува за да го утврди идентитетот на корисникот. Ако JWT-проверката е погрешна, дури и добро изведениот OAuth тек може да заврши со прифаќање фалсификуван идентитет или привилегија.

Во оваа лабораторија се проверуваат три одделни грешки: прифаќање `alg: none`, користење слаба HMAC тајна и мешање на RS256 со HS256. Тие се документирани како класични JWT имплементациски ризици во [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html). Лабораторијата не тврди дека современа JWT библиотека стандардно ги содржи овие пропусти. Ранливите проверки се намерно напишани рачно, за точно да се види погрешната одлука на серверот.

### 3.2. Што мора да одлучи серверот?

Серверот однапред треба да знае каков токен очекува: од кој издавач, за која апликација, со кој алгоритам и со кој клуч. Полето `alg` во токенот е податок доставен од испраќачот, а не дозвола серверот да смени начин на проверка. При валидација се проверуваат и релевантните claims, вклучително `iss`, `aud`, `exp` и `nbf` кога се применливи. Декодирање на `payload` без проверка на потписот не е автентикација.

Практичните напади подолу се сведени на грешките во изборот на алгоритам и клуч. Затоа тест-токените не содржат временски claims. Во вистинска апликација тоа би било дополнителен недостаток; изворниот код од лабораторијата **не смее** да се земе како комплетен пример за безбеден JWT валидатор.

## 4. Практичен дел: три JWT сценарија

### 4.1. Околина и безбедносни граници

Потребни се Docker со Compose, слободна локална порта `3000`, терминал и Python 3 на основниот систем. Node.js работи внатре во контејнерот, па не треба посебна локална инсталација. Доволни се 4 GB RAM за двата лабораториски дела. На Windows командите се извршуваат во WSL2/Ubuntu; на macOS и Linux во Terminal. Проверката на Docker е опишана во секција 2.3. За Python извршете `python3 --version`; ако командата не постои, инсталирајте Python 3 од [официјалната страница](https://www.python.org/downloads/) или преку системскиот пакетен менаџер. Скриптата користи само стандардни Python модули — не треба PyJWT или други пакети.

JWT апликацијата е намерно ранлива. Не ја поставувајте на јавен сервер, не ја врзувајте на `0.0.0.0` на домаќинот и не внесувајте вистински податоци. Во `lab/jwt/compose.yaml` портата е објавена само на `127.0.0.1:3000`. Docker bridge-мрежата не гарантира целосна изолација од интернет; за построг услов користете одделна виртуелна машина без мрежна врска откако ќе ја преземете основната слика. Лабораторијата не создава volumes. RSA клучевите и силната HMAC тајна се создаваат во меморија при стартување и се губат по запирањето.

### 4.2. Подигнување и запознавање со рутите

Отворете терминал во папката `lab/jwt` од приложениот проект. На Windows, во File Explorer отворете ја папката и внесете `wsl` во адресната лента; на macOS/Linux внесете `cd ` и повлечете ја папката во Terminal. Проверете ја локацијата:

```bash
docker compose config --services
```

Очекуваниот излез е `jwt-lab`. Потоа стартувајте:

```bash
docker compose up --build -d
docker compose ps
```

При првото стартување Docker ја презема Node.js сликата ако не е локално достапна. Во `docker compose ps` сервисот треба да има статус `Up`. Отворете `http://127.0.0.1:3000` во прелистувач или извршете `curl http://127.0.0.1:3000/`; се враќа JSON со имињата на рутите. Ако портата е зафатена, најпрво запрете ја апликацијата што ја користи; не менувајте ја Compose врската кон јавен интерфејс.

| Рута | Намена |
|---|---|
| `POST /login` | Издава HS256 токен за тест-корисник со улога `user` |
| `GET /admin` | Намерно прифаќа непотпишан токен (`alg: none`) |
| `GET /admin-alg-safe` | Прифаќа само HS256, но сè уште користи слаба тајна |
| `GET /admin-secret-safe` | Прифаќа HS256 со случајна 32-бајтна тајна |
| `GET /rsa-token` | Враќа примерен RS256 токен и јавен RSA клуч |
| `GET /confusion-demo` | Намерно го прифаќа јавниот RSA клуч како HMAC тајна |
| `GET /confusion-demo-safe` | Прифаќа само RS256 со јавниот RSA клуч |

Во терминалот понатаму работете од истата папка. На некои Windows инсталации командата е `python` наместо `python3`; заменете ја само првата зборовна единица во командите ако е потребно.

### 4.3. Сценарио А — `alg: none`

Токен со `alg: none` нема потпис. Во ранливата функција `verifyVulnerableNone()` во `app.js`, серверот гледа што пишува во header-от и, ако вредноста е `none`, го враќа payload-от без криптографска проверка. Напаѓачот затоа може да запише `role: admin` во свој токен. Ова не е „пробивање“ на HMAC; проверката целосно се прескокнува.

Извршете:

```bash
python3 attacks.py none
```

Скриптата составува два Base64URL дела и остава празен трет дел (токенот завршува со точка). Го испраќа истиот токен до двете рути. Очекуваниот резултат е:

```text
Ранлива /admin: HTTP 200 — {"message":"Добредојде, attacker","role":"admin"}
Заштитена /admin-alg-safe: HTTP 401 — {"error":"Недозволен алгоритам"}
```

Првата рута ја прифаќа измислената улога. Втората однапред бара HS256 и одбива токен без потпис. Во продукциски систем ова треба да го спроведува одржувана JWT библиотека со експлицитно конфигуриран дозволен алгоритам, не рачна проверка на текстот во header-от [7].

### 4.4. Сценарио Б — слаба HMAC тајна

HS256 користи симетричен клуч: истиот таен клуч е потребен за потпишување и проверка. Ако клучот е погодлив збор, напаѓач со еден валиден токен може **офлајн** да пресметува HMAC за кандидатите и да ги споредува со потписот. Нема потреба да испраќа многу барања до серверот. Во лабораторијата намерно е поставена вредноста `secret123`.

Извршете:

```bash
python3 attacks.py weak
```

Скриптата најпрво прави легитимна тест-најава како `alice` со лозинка `demo-pass`, потоа пробува шест кратки кандидати. Кога потписот ќе се совпадне, создава нов токен со `role: admin`. Очекувано:

```text
Пронајдена слаба тајна: 'secret123' (обид 4)
Слаб клуч и фиксен алгоритам: HTTP 200 — ...
Силен клуч и фиксен алгоритам: HTTP 401 — ...
```

Овој случај е важен затоа што `/admin-alg-safe` **правилно** го ограничува алгоритмот, но сепак го прифаќа фалсификуваниот токен: потписот навистина е пресметан со истиот слаб клуч. За споредба, `/admin-secret-safe` користи криптографски случајна 32-бајтна HMAC тајна и го одбива истиот токен. Во вистински систем тајната треба да се генерира со криптографски сигурен генератор, да се чува надвор од изворниот код, да не се користи за повеќе издавачи и да се ротира по компромитирање. [RFC 8725, секција 3.5](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.5) предупредува да не се употребуваат човечки запаметливи лозинки како HMAC клучеви.

### 4.5. Сценарио В — мешање на RS256 и HS256

Кај RS256 издавачот потпишува со **приватен** RSA клуч, а примачот проверува со соодветниот **јавен** клуч. Јавниот клуч не е тајна. Ранливата функција `verifyVulnerableConfusion()` погрешно дозволува токенот да избере HS256 и тогаш го користи текстот на јавниот RSA клуч како HMAC тајна. Напаѓач што го знае јавниот клуч може да изработи валиден HMAC потпис за измислен admin payload. Токму овој вид забуна е опишан во [RFC 8725, секција 2.1](https://www.rfc-editor.org/rfc/rfc8725.html#section-2.1).

Извршете:

```bash
python3 attacks.py confusion
```

Скриптата го зема јавниот клуч од `/rsa-token`, создава HS256 токен со тој клуч како HMAC тајна и го испраќа до ранливата и заштитената рута. Очекувано:

```text
Ранлива /confusion-demo: HTTP 200 — {"role":"admin", ...}
Заштитена /confusion-demo-safe: HTTP 401 — {"error":"Недозволен алгоритам"}
```

Заштитената рута прифаќа само RS256. Дури и ако токенот тврди дека користи HS256, таа нема да го употреби јавниот клуч како симетрична тајна. Во реална OIDC интеграција јавните клучеви често се објавуваат преку JWKS; тоа е очекувано и само по себе не е слабост. Слабоста е погрешната употреба на клучот во валидаторот.

### 4.6. Проверка, ограничувања и бришење

Сите три проверки може да се пуштат одеднаш:

```bash
python3 attacks.py all
```

Скриптата завршува без Python грешка само ако се добијат очекуваните HTTP статуси: `200` на трите ранливи проверки и `401` на соодветните заштитени проверки. Тестот ја потврдува конкретната лабораториска логика, но не претставува пенетрационен тест на вистински OAuth/OIDC провајдер.

По завршувањето, во истата папка извршете:

```bash
docker compose down --rmi local
```

Командата ги отстранува JWT контејнерот, неговата Docker мрежа и локално изградената лабораториска слика. Не се користат volumes. Проверете со `docker compose ps` дека сервисот веќе не работи. Командата не ја брише основната преземена Node.js слика и не е тврдење дека компјутерот е во апсолутно идентична состојба како пред инсталацијата на Docker.

## 5. Заеднички заклучок

OAuth и JWT пропустите во овој елаборат се појавуваат на различни места. Кај Login CSRF, клиентот прифаќа OAuth одговор без да провери дека прелистувачот ја започнал истата трансакција. Кај JWT примерите, серверот или му дозволува на токенот да ја диктира криптографската проверка, или користи предвидлив HMAC клуч. Резултатите од локалните вежби се сумирани подолу.

| Сценарио | Набљудуван исход | Потребна заштита |
|---|---|---|
| OAuth Login CSRF | Жртвата се најавува во сметка на напаѓачот | Трансакциски врзан `state` или соодветно имплементиран PKCE |
| JWT `alg: none` | Непотпишан admin токен е прифатен | Фиксен дозволен алгоритам и проверен потпис |
| JWT слаба тајна | Фалсификуван HS256 токен е прифатен | Силен, случаен и заштитен HMAC клуч |
| JWT RS256→HS256 | Јавен RSA клуч е злоупотребен како HMAC тајна | Строго одделување на алгоритам и тип на клуч |

За продукциска имплементација не е доволно да се пренесат само овие поправки. Потребни се и HTTPS, ограничени дозволи и рокови на токените, проверка на `iss`/`aud`/`exp`, соодветно управување со клучевите, безбедно складирање на сесии и редовно ажурирани библиотеки. Најважно е секој одговор и секој токен да се проверува според контекст што серверот го утврдил **пред** да го добие непроверениот влез.
